# Creker

Android-приложение для личного учёта экранного времени. Название и иконка — от
печенья-крекера в виде часов: круглый счётчик времени, который потихоньку крошится. Читает статистику
использования локально, через системный API `UsageStatsManager`, накапливает её в
локальной базе Room и показывает, сколько времени вы провели в каждом приложении
за выбранный период. Полностью offline: разрешения `INTERNET` в манифесте нет,
данные не покидают устройство.

## Функционал

* **Экран разрешения.** «Доступ к данным об использовании» (`PACKAGE_USAGE_STATS`) —
  специальное разрешение, его нельзя запросить диалогом. При первом запуске
  показывается экран с объяснением и кнопкой на системный экран
  (`ACTION_USAGE_ACCESS_SETTINGS`); статус перепроверяется при каждом возврате
  в приложение.
* **Переключатель периода** — одна кнопка вверху, листается стрелками влево/вправо
  или тапом открывает меню: Сегодня / Вчера / Последняя неделя / Последний месяц /
  свой диапазон (календарь Material 3). Тот же элемент используется на детальном
  экране приложения — выглядит и работает одинаково.
* **Общее время экрана** за период — крупно, в формате `чч:мм:сс` (`02:15:40`).
  Часы не сворачиваются в сутки: месячная сумма выглядит как `127:45:10`.
* **Список приложений** за период: иконка, название, время в `чч:мм:сс` и доля
  от общего времени в процентах, сортировка от самого используемого к наименее
  используемому.
* **График распределения времени** в той же карточке, что и общий итог, с
  переключателем «столбики / линия». Для дня — почасовая разбивка (00:00–23:00);
  для недели, месяца и произвольного периода длиннее суток — по одному значению
  на каждый день диапазона.
* **Детальный экран приложения** — по тапу на строку в списке. Своя карточка с
  графиком и сетка плиток: использование и число сеансов за выбранный период,
  среднее время в день, текущая и максимальная серия дней подряд с использованием,
  максимум за один день и дата установки.
* **Три метрики в каждом графике**, переключаются чипами: время использования,
  число сеансов (заходов в приложение) и экранное время устройства — сколько
  реально горел экран, за вычетом времени на самом экране блокировки.
* **Тап по линии** на графике показывает всплывающую подсказку с точным
  значением; **столбики подписаны сразу**, без нажатия, и подписаны на всей оси
  (00–23 для часового графика). График растягивается щипком в обе стороны —
  по горизонтали (шире точки, удобнее часовой график) и по вертикали (выше
  столбики, легче сравнивать близкие по высоте значения) — и листается пальцем
  в обоих направлениях.
* **Сохранение всех данных** — кнопка в шапке экспортирует всю локальную историю
  (по каждому приложению и по экрану устройства) в CSV через системный диалог
  «Сохранить как», на выбранное пользователем место на устройстве или в облаке.

Намеренно не добавлено: лимиты, напоминания, уведомления, блокировка приложений —
только просмотр статистики. Серии использования показаны как факт (сколько дней
подряд открывали приложение), без геймификации — никаких значков, наград или
подталкивающих сообщений вокруг них.

## Как считается время

`UsageStatsManager.queryUsageStats()` возвращает готовые суммы, но они привязаны
к системным «корзинам» и на произвольном интервале дают неточный результат.
Поэтому приложение работает с сырым потоком событий `queryEvents()` и само
собирает сессии:

1. `ACTIVITY_RESUMED` (`MOVE_TO_FOREGROUND`) открывает сессию приложения.
2. Сессию закрывает `ACTIVITY_PAUSED`, выход другого приложения на передний план,
   выключение экрана (`SCREEN_NON_INTERACTIVE`) или появление экрана блокировки
   (`KEYGUARD_SHOWN`) поверх, или выключение устройства. Учитывать это обязательно:
   часть прошивок не шлёт `PAUSED`, и телефон, забытый на столе, «накрутил» бы часы
   использования.
3. Незакрытая сессия обрезается текущим моментом, а не концом запрошенного окна.
4. Сессии, пересекающие полночь, режутся по локальной полуночи и попадают в оба дня.

**Экранное время устройства** считается отдельно и по-другому: интервал «экран
горит» открывается по `SCREEN_INTERACTIVE` и закрывается по `SCREEN_NON_INTERACTIVE`,
а из него вычитается интервал «показан экран блокировки»
(`KEYGUARD_SHOWN` → `KEYGUARD_HIDDEN`) — то есть само время экрана блокировки не
засчитывается. Если у пользователя вообще нет блокировки экрана, вычитать нечего,
и время экрана засчитывается целиком.

Логика вынесена в `core/` и не зависит от Android — она покрыта unit-тестами
(`app/src/test/.../core`), включая вычитание интервалов для экранного времени.

## Хранение

Room, таблица `app_usage`:

| колонка        | тип     | описание                          |
|----------------|---------|-----------------------------------|
| `package_name`  | TEXT    | пакет приложения (часть PK)         |
| `date`          | TEXT    | день в формате `yyyy-MM-dd` (PK)    |
| `usage_millis`  | INTEGER | время использования за этот день    |
| `launch_count`  | INTEGER | сколько раз приложение открывали    |

Таблица `device_usage` — то же самое, но для экранного времени устройства целиком,
без привязки к пакету:

| колонка         | тип     | описание                                    |
|-----------------|---------|---------------------------------------------|
| `date`          | TEXT    | день в формате `yyyy-MM-dd` (PK)            |
| `screen_millis` | INTEGER | экранное время за этот день, без блокировки |
| `updated_at`    | INTEGER | до какого момента (epoch millis) сумма за этот день полна; `0` — неизвестно |

Вспомогательная таблица `sync_state` хранит момент последней синхронизации,
чтобы не пересчитывать данные заново каждый раз.

Система хранит подробные события всего несколько дней, поэтому:

* **при первом запуске** импортируется вся доступная история — последние 7 дней;
* `UsageSyncWorker` (WorkManager) запускается **раз в сутки, сразу после полуночи**,
  и сохраняет закончившийся день, чтобы данные накапливались на недели и месяцы
  вперёд;
* пересчитываются только те дни, которые ещё можно восстановить из событий, —
  более старые записи остаются нетронутыми (иначе долгий перерыв в запусках
  стирал бы уже накопленную историю);
* пересчёт целыми днями делает повторную синхронизацию идемпотентной;
* если система вернула пустой поток событий (например, доступ отозвали),
  сохранённые дни не затираются.

Пока истории меньше, чем охватывает выбранный период, на экране показывается
пояснение, с какой даты данные реально есть.

График для дня — исключение из этой схемы хранения: почасовая раскладка Room
не хранит (только дневные суммы), поэтому для дня она каждый раз считается заново
из событий системы напрямую, как в `sync()`. Из тех же соображений почасовой
график строится только для сегодняшнего дня — для произвольного дня в прошлом
подробных событий у системы уже может не остаться, и график получился бы
обманчиво пустым; вместо этого показывается однодневная точка на дневном графике.

Детальный экран приложения читает историю иначе: не за выбранный период, а
**всю** локально сохранённую (до 400 дней) — сериям и максимуму за день нужно
видеть дальше одного периода.

Схема менялась трижды (`launch_count`, таблица `device_usage`, затем
`updated_at`) — сейчас версия 4. По умолчанию база пересоздаётся
(`fallbackToDestructiveMigration`): вся история и так выводится из системы и
досчитывается заново по мере работы приложения. Но для `device_usage` это уже не
так безобидно — её читает второе приложение, а система отдаёт назад только
последнюю неделю, — поэтому переход 3 → 4 написан явной миграцией
(`ALTER TABLE … ADD COLUMN`), и накопленные дни переживают обновление.

## Что читает второе приложение

`device_usage` доступна другим приложениям на устройстве через read-only
`ContentProvider` — так приложение-трекер привычек может спросить «сколько было
экранного времени такого-то числа», не заставляя creker получать доступ в сеть.
Наружу отдаётся только устройство целиком: `app_usage`, то есть какими именно
приложениями пользовались, не выходит за пределы creker.

| что                | значение                                                |
|--------------------|---------------------------------------------------------|
| authority          | `com.creker.screentime.provider`                        |
| URI                | `content://com.creker.screentime.provider/device_usage` |
| запрос             | `query(uri, null, null, arrayOf(fromDate, toDate), null)`, обе даты `yyyy-MM-dd`, включительно |
| колонки курсора    | `date`, `screen_millis`, `updated_at`                   |
| разрешение чтения  | `com.creker.screentime.permission.READ_USAGE`, `normal` |
| запись             | закрыта `writePermission` уровня `signature` и безусловным отказом в самом провайдере |

`updated_at` — момент, **до которого** сумма за этот день полна, а не момент
записи строки: для завершившегося дня это его собственная полночь, для текущего —
время последней синхронизации. Без него ноль за сегодня неотличим от «сегодня
никто не считал», а считается текущий день только при открытии creker или после
полуночи воркером.

Все эти имена собраны в одном файле — `contract/UsageContract.kt`. Room берёт
имена таблицы и колонок оттуда же, так что переименование колонки — это правка
контракта, а не незаметная правка сущности; `UsageContractTest` (обычный
JVM-тест) дополнительно сверяет значения с манифестом. Менять их можно только
вместе с приложением-потребителем.

## Сохранение данных

Кнопка в шапке главного экрана открывает системный диалог «Сохранить как»
(`ACTION_CREATE_DOCUMENT`) и пишет всю локальную историю в CSV по выбранному
пользователем пути — на устройство, в подключённое облачное хранилище, куда
угодно. Формат: `type,package_name,date,value_millis,launch_count`, где
`type` — `app` (строка из `app_usage`) или `screen` (из `device_usage`, без
`package_name`). Это единственная операция записи файла в приложении, и она
выполняется только туда, куда явно указал пользователь.

## Оформление

Палитра снята прямо с иконки: печёное золото (`#E9A63C`) на почти чёрном (`#17110C`),
подрумяненный край для вторичных акцентов. Динамический цвет Android 12+
(`dynamicColorScheme`) **намеренно не используется** — он полностью перекрывал
палитру приложения обоями пользователя, из-за чего приложение выглядело не собой.

Все длительности и счётчики набраны моноширинным шрифтом: это часы, цифры в них
постоянно меняются, и на пропорциональном шрифте показания дёргаются при каждом
обновлении секунды. Проза остаётся системным шрифтом.

## Стек

Kotlin, MVVM (ViewModel + `StateFlow` + репозиторий), Jetpack Compose
(Material 3, тёмная и светлая тема по системной), Room, WorkManager,
Coroutines/Flow. `minSdk 26`, `compileSdk`/`targetSdk 35`, Java 17, Gradle 8.11.1,
AGP 8.7.3. Зависимости внедряются вручную через `AppContainer` — граф слишком мал,
чтобы тянуть DI-библиотеку.

```
app/src/main/java/com/creker/screentime/
├── contract/      # то, что обещано наружу: authority, URI, имена колонок, разрешения
├── core/          # чистый Kotlin: сессии, периоды, форматирование чч:мм:сс
├── data/
│   ├── local/     # Room: app_usage, device_usage, DAO, база (internal)
│   ├── system/    # UsageStatsManager, PackageManager, проверка разрешения
│   ├── provider/  # read-only ContentProvider для второго приложения
│   └── UsageRepository.kt
├── work/          # ежедневная фоновая синхронизация
└── ui/
    ├── chart/       # переиспользуемый график: canvas, зум/пан, тултип, селектор метрики
    ├── period/      # переиспользуемая кнопка выбора периода (степпер + меню пресетов)
    ├── stats/       # экран статистики: карточка с графиком, список приложений
    ├── appdetail/   # детальный экран одного приложения: график, плитки со статистикой
    └── permission/  # экран запроса разрешения
```

`QUERY_ALL_PACKAGES` нужен, чтобы на Android 11+ получать названия и иконки
приложений, о которых сообщил `UsageStatsManager`.

## Сборка

```bash
./gradlew assembleDebug          # APK → app/build/outputs/apk/debug/app-debug.apk
./gradlew testDebugUnitTest      # unit-тесты
```

Нужны JDK 17 (или 21) и Android SDK с API 35. JDK 25 несовместим с текущим
Android Gradle Plugin.
